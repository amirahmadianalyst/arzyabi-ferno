# سامانه ارزیابی عملکرد پرسنل رستوران فرنو

سامانه‌ای واقعی (نه Demo) برای ارزیابی هفتگی عملکرد پرسنل، بر پایه دقیق فایل‌های Excel موجود.
تمام معیارها، ضرایب و فرمول‌های محاسبه امتیاز مستقیماً از فایل‌های Excel آپلود‌شده استخراج شده‌اند
(به `ANALYSIS.md` مراجعه کنید).

## ⚠️ نکته مهم درباره اجرا در این محیط تحلیل

این پروژه در محیطی بدون دسترسی به اینترنت ساخته شده، بنابراین **امکان اجرای `npm install` و بالا
آوردن واقعی سرور در همین محیط وجود نداشت**. تمام فایل‌ها به‌صورت کامل نوشته و از نظر Syntax با
`node --check` و `esbuild` تست شده‌اند (بدون خطا)، اما تست عملکردی end-to-end را باید روی
سیستم خودتان (که به اینترنت دسترسی دارد) انجام دهید. مراحل زیر را به ترتیب دنبال کنید.

## ۱. پیش‌نیازها

- Node.js نسخه ۱۸ یا بالاتر (نسخه ۲۰+ توصیه می‌شود)
- npm (همراه Node نصب می‌شود)

## ۲. نصب

```bash
# نصب وابستگی‌های Backend
cd backend
npm install

# نصب وابستگی‌های Frontend
cd ../frontend
npm install
```

## ۳. تنظیم متغیرهای محیطی Backend

```bash
cd backend
cp .env.example .env
```

فایل `.env` را باز کنید و در صورت نیاز مقادیر را تغییر دهید:

```
PORT=4000
JWT_SECRET=یک-مقدار-تصادفی-و-امن-بگذارید
ADMIN_USERNAME=admin
ADMIN_PASSWORD=رمز-عبور-دلخواه
```

## ۴. ایجاد فایل Excel مرکزی و Import اطلاعات اولیه

```bash
cd backend
npm run import:excel
```

این دستور:
- فایل `data/ferno_evaluations.xlsx` را (اگر وجود نداشته باشد) با تمام Sheetهای لازم می‌سازد.
- بخش‌ها (سالن، کال‌سنتر، صندوق، آشپزخانه، تولید) را وارد می‌کند.
- پرسنل هر بخش را دقیقاً از روی Sheet «مرجع» فایل‌های اصلی وارد می‌کند.
- برای هر نقش ارزیاب (مسئول، بازرس، بهداشت، تیم فروش، دوربین، منابع انسانی) یک کاربر نمونه با
  دسترسی صحیح می‌سازد (رمز عبور همه: `eval123`).

**نکته**: از این نسخه به بعد، سال/ماه/هفته دیگر دستی وارد نمی‌شود؛ به‌صورت خودکار از تاریخ واقعی
سرور (به وقت تهران) محاسبه می‌شود — بخش ۱۳ همین README را ببینید.

از مقادیر `ADMIN_USERNAME` و `ADMIN_PASSWORD` در فایل `.env` استفاده می‌کند.

## ۹. ساختار فایل Excel مرکزی (`data/ferno_evaluations.xlsx`)

| Sheet | کاربرد |
|---|---|
| `Evaluations` | یک ردیف به ازای هر ارزیابی ثبت‌شده (پرسنل، ارزیاب، فرم، دوره، میانگین امتیاز) |
| `Evaluation_Scores` | نمره تک‌تک معیارها برای هر ارزیابی (رابطه یک‌به‌چند با Evaluations) |
| `Employees` | فهرست پرسنل و بخش هرکدام |
| `Users` | کاربران سامانه (رمز عبور به‌صورت Hash شده با bcrypt ذخیره می‌شود) |
| `Departments` | فهرست بخش‌ها |
| `Periods` | (میراثی/غیرفعال) در نسخه فعلی استفاده نمی‌شود؛ تاریخچه دوره‌ها اکنون مستقیماً از Sheet `Evaluations` استخراج می‌شود |
| `Audit_Log` | رویدادهای مهم (ورود، ویرایش ارزیابی) |
| `Manual_Scores` | مقدار دستی ستون «سیستم» در فایل ارزیابی کل (توضیح در ASSUMPTIONS) |
| `Bonus_Records` | رکوردهای روزانه پاداش/جریمه (منطق مجزا از ارزیابی‌های معمولی) |

`data/backups/ferno_evaluations_<تاریخ>_<ساعت>.xlsx` گرفته می‌شود.

## ۱۰. منطق محاسبه امتیاز (دقیقاً طبق Excel)

هر فرم ارزیابی (مثلاً «نمره دهی بازرس» برای بخش «آشپزخانه») دارای معیارهایی با ضریب مشخص و یک
مقسوم‌علیه (Divisor) است که همگی از فرمول واقعی داخل سلول `Score` در Excel استخراج شده‌اند. مثال
(بخش آشپزخانه، فرم بازرس):

```
Score = ((رعایت بهداشت × 2) + (پوشش × 2) + چک‌لیست + عملکرد + سرعت + دقت + هماهنگی بین بخش + ارزیابی کل) / 10
```

سپس در فایل «ارزیابی کل پرسنل»، امتیاز نهایی هر پرسنل از ترکیب وزن‌دار خروجی («Score») چند فرم
مختلف به‌دست می‌آید. مثلاً برای بخش آشپزخانه/تولید:

```
Final = ((مسئول × 1.25) + (سیستم × 1.25) + (دوربین × 0.75) + (منابع‌انسانی × 0.25)
         + (بهداشت × 0.75) + (بازرس × 0.75)) / 5
```

این وزن‌ها به ازای هر بخش در `backend/src/config/formsConfig.js` (شیء `MASTER_WEIGHTS`) دقیقاً
مطابق Excel وارد شده‌اند. Endpoint مربوطه: `GET /api/evaluations/master-score`.

## ۱۱. دوره خودکار و روزهای مجاز ارزیابی (پنجشنبه/جمعه)

طبق درخواست، سال/ماه/هفته دیگر توسط ادمین وارد نمی‌شود. سامانه هر بار به‌صورت زنده از تاریخ واقعی
سرور (تبدیل‌شده به وقت تهران، مستقل از منطقه زمانی خود سرور — مثلاً Render که UTC است) این مقادیر
را محاسبه می‌کند (`backend/src/utils/persianDate.js`):

- **سال/ماه شمسی**: با تبدیل میلادی→شمسی (الگوریتم استاندارد و متن‌باز، بدون نیاز به پکیج خارجی).
- **هفته**: `ceil(روز ماه / 7)` — یعنی روزهای ۱ تا ۷ = هفته ۱، ۸ تا ۱۴ = هفته ۲ و... (این یک
  **ASSUMPTION** است چون Excel مفهوم دقیق «هفته» را تعریف نکرده بود).
- **روز مجاز ارزیابی**: فقط پنجشنبه و جمعه.

قوانین اعمال‌شده در `POST /api/evaluations`:

| نقش | رفتار |
|---|---|
| **Evaluator** | فقط در پنجشنبه/جمعه می‌تواند ارزیابی ثبت کند؛ در روزهای دیگر خطای ۴۰۳ با پیام «روزهای مجاز ثبت ارزیابی پنجشنبه و جمعه است» دریافت می‌کند. سال/ماه/هفته همیشه توسط سرور محاسبه می‌شود و از ورودی کلاینت قابل تغییر نیست. |
| **Admin** | **همیشه** و در **همه روزها** می‌تواند ارزیابی ثبت/مشاهده/ویرایش کند (طبق درخواست: «تمام دسترسی‌های ادمین همیشه باز باشد»)؛ در صورت نیاز می‌تواند حتی سال/ماه/هفته را صریحاً برای ثبت دستی/اصلاحی مشخص کند. |

صفحه ادمین «دوره‌های ارزیابی» (`/admin/periods`) اکنون فقط‌خواندنی است و دوره فعلی + تاریخچه
دوره‌هایی که واقعاً برایشان ارزیابی ثبت شده را نمایش می‌دهد (بدون فرم ورود دستی).

### نشانگر سبز پرسنل ارزیابی‌شده
در صفحه «ارزیابی جدید»، هنگام انتخاب پرسنل، هر کسی که همان ارزیاب برای فرم و دوره جاری قبلاً
ارزیابی‌اش را ثبت کرده باشد، با رنگ سبز و علامت ✓ مشخص می‌شود تا مسئول به‌سرعت ببیند چه کسانی
باقی مانده‌اند (Endpoint: `GET /api/evaluations?department=..&formId=..&year=..&month=..&week=..`
که به‌خاطر Permission موجود، برای Evaluator فقط ارزیابی‌های خودش را برمی‌گرداند).

## ۱۲. Bonus / پاداش (منطق مجزا)

چهار Sheet پاداش در فایل «ارزیابی کل پرسنل» (کانتر سالن، کانتر ارسال، سرپیک، سراپراتور) بر خلاف
فرم‌های ارزیابی معمولی، بر مبنای **کسر جریمه از یک مبلغ پایه روزانه** کار می‌کنند، نه میانگین
امتیاز. این منطق در `backend/src/config/referenceData.js` (`BONUS_ROLES`) و
`backend/src/routes/bonus.js` به‌صورت کاملاً جدا پیاده‌سازی شده است. رابط کاربری آن نیز مسیر
مجزای `/bonus` (برای Evaluator) و `/admin/bonus` (برای ادمین) دارد.

## ۱۳. ASSUMPTIONS (فرضیات مستندشده طبق درخواست شما)

طبق «قانون عدم حدس»، تمام موارد زیر تنها مواردی هستند که در Excel به‌صورت قطعی قابل تشخیص نبودند:

1. **ستون «System» (سیستم)** در فایل «ارزیابی کل پرسنل»: در هیچ‌کدام از ۶ فایل «نمره دهی ...»
   ستونی با این عنوان یا خروجی معادل آن یافت نشد. بنابراین این مقدار به‌صورت **ورودی دستی ادمین**
   (Sheet `Manual_Scores`، Endpoint `POST /api/evaluations/manual-score`) طراحی شده است. اگر این
   مقدار در سازمان شما منبع مشخصی دارد (مثلاً چک‌لیست سیستم POS)، لطفاً اطلاع دهید تا فرم مربوطه
   نیز اضافه شود.
2. **بخش‌های Bonus** (کانتر سالن/ارسال، سرپیک، سراپراتور): در داده‌های نمونه Excel، این نقش‌ها
   عمدتاً توسط یک یا دو نفر مشخص (یا مقدار «-») پر شده بودند، نه یک لیست پرسنل ثابت مانند سایر
   بخش‌ها. بنابراین در پیاده‌سازی، نام پرسنل برای این بخش به‌صورت متن آزاد وارد می‌شود (نه انتخاب از
   لیست).
3. **دسترسی به فرم‌های Bonus**: در Excel مشخص نشده کدام نقش مسئول ثبت این فرم‌هاست. فرض شده که
   هم ادمین و هم هر کاربر Evaluator با هر نقشی (معمولاً «مسئول بخش») بتواند این رکوردها را ثبت کند؛
   در صورت نیاز به محدودسازی دقیق‌تر، در `routes/bonus.js` قابل تغییر است.
4. **«انتظار تعداد ارزیابی» در داشبورد Evaluator**: چون Excel مشخص نمی‌کند هر ارزیاب باید دقیقاً چند
   ارزیابی در هر دوره ثبت کند، این عدد به‌صورت (تعداد پرسنل بخش‌های مجاز) × (تعداد فرم‌های مجاز)
   تخمین زده شده است.
5. **تعریف «هفته» در محاسبه خودکار دوره**: چون در Excel مشخص نبود «هفته» دقیقاً بر چه اساسی شماره‌گذاری
   می‌شود، فرمول `ceil(روز ماه شمسی / 7)` در نظر گرفته شد (بخش ۱۱). اگر تعریف دیگری در سازمان شما
   رایج است (مثلاً هفته‌ها از شنبه شروع شوند و با تقویم هفتگی واقعی همسو باشند)، اطلاع دهید تا
   `backend/src/utils/persianDate.js` اصلاح شود.

## ۱۴. تست‌های پیشنهادی (طبق چک‌لیست شما)

پس از بالا آوردن هر دو سرویس، این سناریو را دنبال کنید:

1. ورود با کاربر ادمین → مشاهده Dashboard → مشاهده دوره فعلی محاسبه‌شده خودکار.
2. اگر امروز پنجشنبه/جمعه نیست: خروج و ورود با `responsible1` / `eval123` → مراجعه به «ارزیابی جدید»
   → باید پیام «امروز روز مجاز ارزیابی نیست» نمایش داده شود؛ اما ورود مجدد با ادمین و رفتن به
   همان مسیر باید بدون محدودیت کار کند (چون دسترسی ادمین همیشه باز است).
3. اگر امروز پنجشنبه/جمعه است: با `responsible1` / `eval123` وارد شوید.
4. «ارزیابی جدید» → انتخاب بخش «سالن» → انتخاب پرسنل → امتیازدهی معیارهای واقعی → ثبت.
5. به صفحه انتخاب پرسنل برگردید و بررسی کنید نام پرسنلی که تازه ارزیابی شد اکنون سبز و با علامت ✓
   نمایش داده می‌شود.
6. باز کردن `backend/data/ferno_evaluations.xlsx` و بررسی این‌که ردیف جدید در Sheet
   `Evaluations` و `Evaluation_Scores` اضافه شده و هیچ ردیف قبلی از بین نرفته است.
7. تلاش برای ثبت مجدد همان پرسنل/فرم/دوره → باید پیام «قبلاً ثبت شده» نمایش داده شود.
8. ورود با `camera1` و تلاش برای دسترسی مستقیم به فرم «بهداشت» از طریق API → باید ۴۰۳ برگردد.
9. ورود مجدد با ادمین → «ارزیابی‌ها» → فیلتر بر اساس بخش/دوره → دانلود Excel (خام و مدیریتی).
10. بررسی پوشه `backend/data/backups/` برای وجود فایل‌های Backup.

## ۱۵. توسعه آینده (طبق معماری تمیز طراحی‌شده)

برای مهاجرت به PostgreSQL در آینده، کافی است یک فایل جدید

منطق Business (`utils/scoring.js`, `config/formsConfig.js`) کاملاً مستقل از Storage نوشته شده است.
